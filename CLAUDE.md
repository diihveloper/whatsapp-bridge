# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm install` — install deps (Node ≥ 20; `better-sqlite3` ships prebuilt Windows binaries, no MSVC needed).
- `npm start` — run the bridge in foreground. Holds the terminal; open another shell for other commands.
- `npm run dev` — same as start, with `node --watch` auto-reload.
- `npm run install-skill` — copies `skill/whatsapp-assistant/` into `~/.claude/skills/whatsapp-assistant/`. Must restart Claude Code afterwards to pick it up.
- `npm run wl` — interactive whitelist editor (reads `data/messages.db` directly, doesn't need the service running).

No test suite, linter, or build step. The repo is plain ESM (`"type": "module"`) — no transpile.

## Architecture

Three persistence locations, each with a different role:

- `~/.whatsapp-bridge/config.json` (chmod 600) — `apiToken` and `baseUrl`. Generated on first `npm start` by `src/config.js`. The skill reads this same file to learn how to call back.
- `./auth_data/` — Baileys multi-file auth state (Signal Protocol keys). Delete to force re-pairing via QR.
- `./data/messages.db` — SQLite (WAL mode) with `chats`, `messages`, `contacts`, and an FTS5 virtual table `messages_fts` kept in sync via triggers (`messages_ai`/`ad`/`au` — the `au` UPDATE-of-body trigger exists so edits reindex). Schema is created on first run in `src/store.js`. **Anti-delete / edit tracking**: `messages` has `deleted_at` (delete-for-everyone keeps the body and just flags it — `markDeleted`), `edited_at` + `original_body` (`applyEdit` rewrites `body` to the new text but preserves the first `original_body`). These three columns are added by a defensive `ensureColumn` migration (`PRAGMA table_info` + `ALTER TABLE`) so old DBs upgrade in place. `getMessages` returns `deletedAt`/`editedAt`/`originalBody`; never strip a deleted row — preserving it is the whole point. **Media columns** (`media_path`, `media_mime`, `media_status`), added by the same `ensureColumn` migration, back audio transcription / image OCR / document download: `media_status` tracks the `pending`→`done`/`error`/`skipped` lifecycle, and a successful transcription/OCR is **folded into `body`** (via `setMediaText`) so it shows up in reads *and* gets FTS-reindexed by the `messages_au` body trigger — the `type` column still says it was `audio`/`image`. Raw files (only when `STORE_MEDIA` keeps them) live under `./data/media/` (covered by the `data/` gitignore). The `contacts` table is the name → JID resolver, populated from `pushName` (per-message, sender side), `contacts.update.notify` (address-book name), and `contacts.update.name` (verified business name). `chats.name` is only for *chat* names — group titles or DM display names — and is intentionally not used as a person lookup.

Process flow (`src/index.js` wires it up):

1. `loadOrCreateConfig()` generates/reads the API token.
2. `startWhatsApp()` (`src/whatsapp.js`) opens a Baileys socket, prints QR if unauthenticated, and subscribes to `messages.upsert` / `contacts.update` / `chats.upsert`. Inbound messages are normalized by `extractBody()` (handles text / image caption / video caption / audio / document / sticker / reaction) and written through `saveMessage()`.
3. `createServer()` (`src/server.js`) mounts the Express API on `HOST:PORT` (defaults `127.0.0.1:4477`). All routes except `/health` require `Authorization: Bearer <apiToken>`.

**Two connection backends, selected by `BRIDGE_MODE` (`src/index.js`):**

- `baileys` — step 2 above. The socket lives in the service, so `POST /chats/:id/messages` calls `sendText()` directly. Opt in via `BRIDGE_MODE=baileys`.
- `extension` (default) — Baileys is **not** started. The WhatsApp connection lives in a Chrome/Chromium tab via the MV3 extension in `./extension`, which uses `@wppconnect/wa-js` against the official WhatsApp Web client (no new linked device → far lower ban risk than Baileys). The extension pushes normalized messages/contacts to `POST /ingest` and the service can't send directly — `POST /chats/:id/messages` instead **enqueues** into the `outbound` SQLite table (whitelist + `ENABLE_SEND` checks unchanged, still the server-side security boundary), then waits up to 8s for the tab to confirm before returning `200` or `202 {pending}`. The server pushes queued sends to the extension over SSE (`GET /outbound/stream`, token via query param since EventSource can't set headers) so a backgrounded tab — whose timers Chrome throttles — still gets them immediately; `GET /outbound` polling remains as a backstop. `claimPending` atomically marks rows `sending`; the extension reports back via `POST /outbound/:id/result`. The extension flushes ingest straight from the inbound message event (also throttle-immune) rather than on a timer. Besides new messages, `inject.js` subscribes to `chat.msg_revoke` (delete-for-everyone → `revokes:[id]` in `/ingest`, keeps the body and sets `deleted_at` — see "Anti-delete" below), `chat.msg_edited` (the wa-js event is `msg_edited`, *not* `msg_edit` → `edits:[{id,body,timestamp}]` → `applyEdit`), and `chat.new_reaction` (ingested as a normal `type:'reaction'` message row, mirroring the Baileys path). It resolves the **real group title** for group messages (`resolveGroupTitle` → `formattedTitle`/`groupMetadata.subject`, never the sender's `pushName` — that was the historical bug) and, on connect, bulk-corrects every group's name via `syncGroupTitles` (`WPP.chat.list({onlyGroups:true})` → `chatNames:[{id,name}]` in `/ingest` → `updateChatName`). It also reports the tab's connection state (`conn.main_ready`/`require_auth`/`logout`) to `POST /status`, which `/health` surfaces as `connected`/`extension.state` — so in extension mode `/health` reflects whether the WhatsApp Web tab is actually live, not a hardcoded `false`. Because the server keeps that state in memory, a server restart would otherwise leave `/health` stale (ingest keeps working but status reads `unknown`); to fix that, when `bridge.js`'s SSE stream reconnects (`es.onopen`) it asks `inject.js` to re-report (`requestStatus` → `reportCurrentStatus` based on `WPP.conn.isMainReady`), which also re-arms `maybeAutoBackfill` after a restart. Readiness uses wa-js's `WPP.webpack.onFullReady` hook (falling back to polling `isFullReady`) instead of an unbounded `setInterval`. **Backfill**: live ingest only captures messages observed while the tab is open, so gaps from downtime are filled via `WPP.chat.getMessages` paging (`direction:'before'`) — `inject.js`'s `backfillChat` re-ingests history (server dedups by id). Triggered two ways: on demand via `POST /chats/:id/backfill {since,max}` (server pushes a `{backfills:[{reqId,chatId,since,max}]}` command over the same SSE stream as sends, waits up to `BACKFILL_WAIT_MS` for the tab to POST `/backfill/:reqId/result`), and automatically on reconnect — `POST /status` flipping into `connected` calls `maybeAutoBackfill`, which refills unread chats (`chatId:'*'` → `WPP.chat.list({onlyWithUnread:true})`) since the newest stored message (`lastMessageTimestamp()`), debounced by `AUTO_BACKFILL_COOLDOWN_MS`. CORS is allowed only for `chrome-extension://` origins; the Bearer token is still the real auth. The extension's two content scripts run in different worlds (`inject.js` MAIN = `window.WPP`, `bridge.js` ISOLATED = HTTP) and talk via `window.postMessage`. JID normalization happens in `inject.js`: WhatsApp Web's `@c.us` ↔ the DB's `@s.whatsapp.net`. `npm run build-extension` vendors the wa-js bundle from `node_modules` into `extension/vendor/` (gitignored).

**Media processing (transcription / OCR / download)** lives in `src/media/` and is **pluggable + off by default**, selected purely via `.env`: `TRANSCRIBE_PROVIDER` (`off`|`groq`|`openai`|`whisper-local`), `OCR_PROVIDER` (`off`|`claude`|`groq`|`tesseract`), `STORE_MEDIA` (`off`|`processed`|`documents`|`all`). `src/media/index.js` reads env once and dispatches to a provider in `src/media/providers/`; cloud providers (groq/openai/claude) use **only the built-in `fetch`/`FormData`/`Blob`** (zero extra deps — Groq & OpenAI share `openaiCompatible.js` for Whisper and Groq vision uses `openaiCompatibleVision.js`), while `tesseract`/`whisper-local` are **optional deps loaded via dynamic `import()` only when selected** (friendly error if missing; whisper-local also needs `ffmpeg` on PATH to convert WhatsApp's ogg/opus to wav). The module is provider logic only — it never touches the DB or fs. `src/media/process.js` is the shared orchestrator (persist per `STORE_MEDIA` → transcribe/OCR → `setMediaText`); it's best-effort and never throws, so one bad voice note can't break ingest. **Capture differs by backend:** in extension mode `inject.js` downloads bytes (`WPP.chat.downloadMedia` → Blob → base64) for the types `/health` advertises in `media.download` (bridge.js learns them via `refreshMediaConfig` and pushes `{kind:'mediaConfig'}` to inject) and POSTs them to `POST /media` (separate from the ingest batch since bytes are large; retries once on 409 because the ingest flush and the media upload race). The server decodes, enforces `MEDIA_MAX_BYTES` (the `/media` route gets its own larger `express.json` limit; all other routes stay at 2mb), and processes through a **serial queue** (`enqueueMedia`) so it never fires dozens of parallel API calls. In baileys mode `whatsapp.js` downloads via `downloadMediaMessage` and calls `processMedia` directly (no HTTP). **Backfill deliberately skips media download** — re-transcribing thousands of historical audios would surprise the user with cost; only live messages get processed. `GET /chats/:id/messages/:msgId/media` (and the id-only `GET /messages/:msgId/media`) serves a stored file (containment-guarded to `data/media/`). **On-demand fetch**: because live ingest only downloads media for *new* messages of enabled types (and backfill skips media entirely), media that arrived while `STORE_MEDIA` was off isn't on disk. `POST /messages/:msgId/fetch-media` fixes that — it looks the chat up from the message id, pushes a `{mediaFetches:[{reqId,msgId}]}` command over the same SSE stream as sends/backfills, and the tab re-downloads via `WPP.chat.downloadMedia(msgId)` and POSTs it to `/media` with `store:true` (which sets `processMedia`'s `forceStore`, persisting regardless of `STORE_MEDIA`); the route polls the row until the file lands. The original media must still exist on WhatsApp and the tab must be connected. **Gotcha (don't "simplify"):** `inject.js`'s `handleMediaFetch` does **not** call `WPP.chat.downloadMedia(id)` — that re-resolves via `getMessageById`→`MsgKey.fromString`, which throws `createWidFromWidLike` on group messages whose participant is an `@lid` JID. Instead it finds the live message **model** (`WPP.chat.getMessages(chat)` → match by `_serialized`/id-hash), calls `model.downloadMedia({downloadEvenIfExpensive:true,...})`, and reads the decrypted blob from `WPP.whatsapp.LruMediaStore`/`MediaBlobCache` keyed by `mediaData.filehash` (falling back to `mediaData.mediaBlob.forceToBlob()`) — the same retrieval wa-js does internally, minus the id round-trip. If you add a provider, add it to `src/media/index.js`'s dispatch *and* document the env in `.env.example`.

**Daily-use reads (digest / pending) + keyword alerts** are SQL-first and live in `store.js`: `getUnreadDigest` groups unread chats with their recent messages (per-message read state isn't tracked, so "unread" is approximated by the last `unread` messages per chat), and `getPendingReplies` finds chats whose newest message is *not* `fromMe` and is older than `hours` (oldest-waiting first; newsletters/status excluded). `GET /digest` returns that structured data by default and **the caller summarizes** (the recommended, zero-cost path — Claude in a session or a `/schedule` agent); `?summarize=true` optionally runs `src/ai.js` (pluggable `SUMMARY_PROVIDER` = `off`|`groq`|`openai`|`claude`, fetch-only, reuses the media keys) to return prose, and reports `summaryError` when the provider is off rather than failing. **Keyword watchlist**: `src/watchlist.js` mirrors the whitelist pattern (`watchlist.txt` in root, watched + reloaded, `#` comments; substring match, or `/regex/i` for power users). `src/alerts.js` owns the channels — `ALERT_WEBHOOK_URL` (POST JSON; ntfy/Discord/Slack-compatible) and `ALERT_WHATSAPP_TO` (sends via the normal send path, so it needs `ENABLE_SEND` + whitelist). Its `processAlerts(messages, {sendWhatsApp})` is called fire-and-forget from both `/ingest` (extension; `sendWhatsApp` enqueues + SSE-pushes) and `whatsapp.js` (baileys; `sendWhatsApp` is `sendText`). It **always records** a hit (`recordAlert`, `UNIQUE(msg_id,keyword)` dedups → fires each alert once) so `wa alerts` works even with no channels, but only for **fresh** messages (`ALERT_MAX_AGE_MS`, default 15 min) so a history backfill doesn't fire a storm of stale alerts. The `alerts` table and `recordAlert`/`listAlerts` are in `store.js`.

**Per-chat memory (daily/weekly)** lives in `src/memory.js` and is **on-demand only — there is no scheduler**. The intent mirrors Claude Code's session memory: an LLM-written note per (chat, day) and per (chat, week) that records decisions, pending items, facts about the person/group, and tone — *not* a transcript. Persistence is the `chat_memories` table (`UNIQUE(chat_id, period, period_start)` so rebuilding the same window overwrites instead of duplicating). The store helpers (`messagesInRange`, `listChatsWithActivity`, `upsertChatMemory`, `getChatMemories`, `getLatestChatMemory`, `listRecentMemories`) are the only DB surface — `src/memory.js` is provider/transcript logic only. Triggered via `POST /memory/build {chatId?, all?, period:'daily'|'weekly', when?, force?, minMessages?}` and read via `GET /chats/:id/memory` / `GET /memory`; the CLI wraps it as `wa memory show|build|list` (`--all` for batch, `--period weekly`, `--when YYYY-MM-DD` for a past window, `--force` to rebuild). **Cumulative context**: when building a daily memory the orchestrator passes the previous daily + latest weekly as prior context to the LLM, so facts carry forward across cycles; weekly builds prefer the week's own dailies (cheaper, denser) and fall back to raw messages when no daily exists. Eligibility is volume-gated (`MEMORY_MIN_MESSAGES`, default 5) so single-message chats don't burn LLM calls — `listChatsWithActivity` does the filter in SQL. Reuses `SUMMARY_PROVIDER` (no separate config) and fails loudly if it's off. `buildMemoryForAll` runs sequentially (not parallel) to keep rate limits manageable, and idempotently skips windows whose `messageCount` is unchanged unless `force:true`. The `/health` payload reports `memory.{enabled,provider,minMessages}` so callers can detect the feature. Local-time day/week bounds (week = Monday→Monday, ISO).

**Rich send (media + quoted reply)**: `POST /chats/:id/messages` accepts `{text}`, `{text, quotedMsgId}` (reply), or `{media:{path|url}, caption?, quotedMsgId?}`. The `outbound` table grew `kind`/`media_path`/`mime`/`filename`/`caption`/`quoted_msg_id` (via `ensureColumn`). The server *stages* media first (`stageOutboundMedia`: a disk path is used in place; a URL is downloaded into `data/outbound_media/` and flagged `staged`), enforcing `MEDIA_MAX_BYTES`. Crucially, the file bytes are **not** stored in the DB or pushed over SSE up front — `hydrateSends()` reads the file and base64-inlines it into the wire payload only at claim/push time (and fails the send if the file vanished), so the `outbound` table and SSE stay small. The extension's `inject.js` sends via `WPP.chat.sendFileMessage(jid, dataURL, {type,caption,quotedMsg})` (type derived from MIME) or `sendTextMessage(jid, text, {quotedMsg})`; the stored message id is WA's `_serialized` form, so it works directly as `quotedMsg`. Staged URL files are cleaned up after the send confirms (route wait *and* the `/result` handler, covering the timed-out-then-later-confirmed case); disk-path originals are never touched. **baileys** sends media inline via `sendMedia()` (`whatsapp.js`, content shape by MIME) but does **not** quote (would need the original `WAMessage`).

**@mention tracking (`mentions_me`)**: messages carry a `mentions_me` flag (added by `ensureColumn`). The extension computes it in `inject.js` by comparing the message's `mentionedJidList` against the owner's number (`WPP.conn.getMaybeMeUser()`, cached + refreshed on `conn.main_ready`); baileys reads `contextInfo.mentionedJid` vs `sock.user.id`. Comparison is on bare phone digits (ignoring `@c.us`/`@lid`/`@s.whatsapp.net` and device suffixes). `GET /mentions` / `wa mentions` lists them (`getMentions`, groups mostly).

**Conversation export**: there's no server endpoint — `wa export` reuses `/conversation` and renders a clean Markdown transcript (`buildExportMarkdown` in `wa.mjs`) to stdout or `--out file`. The intended flow is *agent + document skill*: export the Markdown, then the assistant builds an LI-styled `.docx`/PDF with the `edicao-documentos-loja-interativa` skill.

**Send path is opt-in twice over**: `ENABLE_SEND=true` env *and* the target chat present in `send_whitelist.txt` (root). `src/whitelist.js` loads the file once, normalizes phone-number entries to `<digits>@s.whatsapp.net`, and `fs.watch`es the directory to reload (debounced 100ms) on save — no restart needed. Empty/missing file means *no chats can be sent to*; this is intentional, never weaken it. `scripts/whitelist.js` is the interactive picker that mutates this same file while preserving manual entries and comments.

**Agent tag on outbound messages** (`SEND_AGENT_PREFIX`): optional env var that prepends a tag (e.g. `[Agente]`, `🤖`) to every outbound text/caption so recipients can tell automation from a human. Empty = off (default). `server.js`'s `withAgentTag` inserts a single space between tag and body unless the tag already ends in whitespace — this is intentional because dotenv strips trailing whitespace on unquoted values, so `SEND_AGENT_PREFIX=[Agente] ` would otherwise land as `[Agente]` and squish to `[Agente]Hello`. The prefix is applied in two places: `POST /chats/:id/messages` (text or media caption) and `deliverWhatsApp` (the internal alert send path, since watchlist alerts are also automation). Per-send override on the POST body: `agentPrefix:false` disables for that one send, `agentPrefix:"..."` overrides. The `wa send` CLI mirrors this with `--no-prefix` / `--prefix "..."`. `/health` reports the active prefix under `send.agentPrefix` so callers can detect tagging is on. If you add a new send path, decide whether automation tagging fits and call `withAgentTag` if so.

**Auto-update check** (`src/updates.js`): on server startup and every 6h, the bridge runs `git fetch --quiet --no-tags` in the repo root and compares `HEAD` to the tracked upstream (resolved via `@{u}`, falling back to `origin/<branch>`/`origin/HEAD`). Result lives in memory (`getUpdateStatus`) and is exposed under `update` in `/health` (`{available, commitsBehind, current, upstream, upstreamRef, lastCheckedAt, error, repoPath}`); `GET /update/commits` returns the commit list between HEAD and upstream (for the CLI to display), and `POST /update/check` forces a fresh fetch. Failures (no `git`, no remote, offline) are recorded in `error` and never throw — the check is best-effort. The actual `git pull && npm install` runs from `wa update` (the CLI shells out locally in `update.repoPath`); doing it server-side would race with node's loaded module cache and surprise the user mid-session. `wa update` refuses on a dirty tree unless `--force`, uses `git pull --ff-only`, and on Windows uses `shell:true` for `npm` (lives as `npm.cmd`). After a successful pull+install the user must restart `npm start` to load the new code.

**Contact name resolution**: `src/aliases.js` mirrors the whitelist pattern (`contacts_aliases.txt` in root, watched, `alias = jid` format, comments with `#`). The `/contacts?q=` endpoint in `src/server.js` first checks the alias map, then falls back to substring search on the `contacts` table. Alias matches are tagged `matchedVia: "alias"` so the skill can treat them as explicit user intent. The whitelist is a *security* boundary (must be edited by the user); aliases are a *convenience* layer (also user-owned, but not a security control). Because of that distinction, aliases get HTTP write endpoints (`POST /contacts/aliases {alias,jid}`, `DELETE /contacts/aliases/:alias` → `addAlias`/`removeAlias`, which rewrite the file preserving comments) but the **whitelist deliberately has no write endpoint** — anything with the API token (including the assistant/skill) could otherwise self-authorize sends, which would defeat the boundary.

**Extension options page** (`extension/options.html` + `options.js`): a management UI that talks to the service over the same Bearer-token HTTP API (its origin is `chrome-extension://`, allowed by CORS). Panels: live `/health` status, alias add/list/remove, **read-only** whitelist view with a chat/contact search that copies a JID to paste into `send_whitelist.txt` (never writes it — see above), and an on-demand backfill trigger. The shared search merges `GET /chats` (so groups appear) with `GET /contacts?q=`. Note CORS now advertises `DELETE` for the alias endpoint.

The skill (`skill/whatsapp-assistant/SKILL.md`) is a documentation-only contract — it tells future Claude sessions how to read WhatsApp, but is decoupled from server code. It now leads with a bundled **CLI** (`skill/whatsapp-assistant/wa.mjs`, copied to `~/.claude/skills/whatsapp-assistant/` by `install-skill`): a zero-dependency Node script that reads the config, authenticates, resolves names→JIDs, optionally backfills, and prints formatted output, so the skill runs one command instead of several curls. It's a thin client over the HTTP API — `npm run wa -- <cmd>` runs it locally. The composite **`GET /conversation?name=…&backfill=…&days=…`** endpoint backs `wa read`: it resolves a name (alias → contacts → chats, returning `{ambiguous,candidates}` when >1 match), optionally backfills, and reads, in one call (`resolveTarget` + `runBackfill`). `getMessages` exposes `senderName` (LEFT JOIN `contacts`) so group senders render as names. If you change endpoints, update both the skill's endpoint table **and** `wa.mjs`.

## Conventions

- Chat IDs are JIDs: `<digits>@s.whatsapp.net` (DM, traditional), `<digits>@lid` (DM, modern Linked-ID system — same person, anonymized identifier), or `<digits>@g.us` (group). The `is_group` flag in the DB is derived purely from the `@g.us` suffix.
- `pushName` is the *sender's* display name, never the chat's. In `messages.upsert`, only DMs use `pushName` as the chat name; for groups it would overwrite the real group title (this was a historical bug — don't reintroduce it). Group names come from `chats.upsert` events.
- Timestamps in the DB are Unix **milliseconds** (Baileys gives seconds; `whatsapp.js` multiplies by 1000 before storing).
- `getMessages()` queries DESC then `.reverse()`s in JS so each page returns oldest→newest while still respecting `LIMIT`. Don't "simplify" this to `ORDER BY ASC`.
- `INSERT OR IGNORE` on `messages.id` is the dedup mechanism for re-delivered messages — duplicates from Baileys are expected, not a bug.
- The auth middleware uses naive `split(' ')` on the Authorization header; don't change to a constant-time compare without also reconsidering the threat model (loopback-only by default, see README "Notas de segurança").
